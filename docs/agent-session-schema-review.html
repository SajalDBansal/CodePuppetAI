The agent-session schema, read end to end

What each model is for, when it gets written, how a tool call and its result actually land in the database, how compaction is created and later consulted — and eight places the current schema needs a second pass before it ships.

Scope AgentSession · AgentInteraction · AgentTurn · AgentMessage · AgentSessionCompaction · UsageEvent Status not yet migrated

The shape is right — five/six tables cleanly separating thread, request, provider call, and content is exactly what a streaming, compactable, multi-turn agent needs, and it already reflects the provider-switching and enum clean-up from the earlier design pass. Eight issues below are worth fixing before the first migration, three of them real correctness risks rather than polish.

01

The six models, plain language

Each model answers a different question about the same conversation. Read top to bottom — they nest inside each other in exactly this order.

AgentSession created once, at chat start

Question it answers: "which conversation is this?" — the thing a user thinks of as one chat, from opening it to archiving it. Long-lived; can span days.

  • written atsession creation — userId, default providerId/modelId, mode, thinkingLevel, systemPrompt
  • updated atevery interaction — lastMessageAt; possibly providerId/modelId if the user switched provider
  • never storesmessage content, token counts — those live one level down
AgentInteraction created per user-sent message

Question it answers: "what did the user ask for, and is the agent still working on it?" One row per POST /agent-sessions/:id/interactions call. A single interaction can span several provider round trips if the model needs a tool result before it can answer.

  • written atthe user's message arrives — providerId/modelId fixed for this interaction's lifetime, status: RUNNING
  • updated atinteraction finishes — status: COMPLETED/ERROR, completedAt, rolled-up inputTokens/outputTokens
AgentTurn created per provider call

Question it answers: "what did this specific call to Google/Anthropic/OpenAI return?" One row per providerRegistry.stream() invocation — the only place provider-specific facts (responseId, stopReason, per-call token usage) belong, since they don't apply to a whole interaction, only to one exchange with the model.

  • written atthe provider stream's done/usage events fire — stopReason, responseId, inputTokens/outputTokens/cachedTokens/reasoningTokens
  • read atthe compaction trigger check, before every next call — compares inputTokens to the model's contextWindow
AgentMessage created for every piece of content

Question it answers: "what was actually said?" The atomic record — one row per user message, per assistant reply, per tool call, per tool result. Everything else in this schema exists to group and order these rows.

  • written atuser sends a message · assistant streams text/a tool call · CLI reports a tool result — every one gets the next sequence number in the session
  • read atcontext assembly for the next provider call, and the "show full history" view — see §5–6
AgentSessionCompaction created when context gets large

Question it answers: "what can replace the old raw transcript so the next provider call still fits in the context window?" Never deletes anything — it's a pointer plus a summary, consulted only when building the next request.

  • written atafter a turn whose inputTokens crosses ~70% of contextWindow — summary, coversFromSequence, coversToSequence
  • read atevery context build — take the newest row, use it in place of the messages it covers
UsageEvent created per turn, for billing/analytics

Question it answers: "what did this cost, and how long did it take?" Distinct from AgentTurn's usage fields on purpose — AgentTurn is the hot-path fact the compaction check reads immediately; UsageEvent is the reporting-shaped row (cost in dollars, latency, arbitrary metadata) a billing dashboard queries later. See finding #1 — right now the token counts are duplicated across both instead of this split being clean.

  • written atafter a turn completes and ModelCatalog pricing is applied — costUsd, latencyMs
  • read atcode-puppet sessions show totals, any future billing export
02

How they connect

AgentSession is the root. Everything else points back to it directly and to its immediate parent — an AgentMessage knows its session, its interaction, and (once one exists) its turn, all three, not just the nearest one. That's deliberate: grouping and billing queries want the nearest parent; replaying history for the model wants the whole set ordered by sequence and doesn't care about parents at all.

03

Storing a tool call and its result

There's no separate ToolCall table — a tool call is fully described by two ordinary AgentMessage rows: the assistant's request, and (later) the result. This keeps the schema small until something needs to track a call's lifecycle independently (pending → running → failed) — not needed yet.

1 — the request (assistant-authored)

Written the moment the provider stream yields a tool_call event:

AgentMessage {
  sequence:  2
  role:      ASSISTANT
  turnId:    "T1"
  content:   null
  toolCalls: [
    { "id": "tc1", "name": "list_files", "arguments": { "path": "src" } }
  ]
  providerMetadata: { "google": { "thoughtSignature": "..." } }
}

2 — the result (tool-authored)

Written once the CLI has actually run list_files locally and reports back:

AgentMessage {
  sequence:   3
  role:       TOOL
  turnId:     null            -- belongs to the *next* turn, not yet created
  toolCallId: "tc1"           -- links back to the request above
  name:       "list_files"
  content:    "index.ts\nutils.ts\ngoogle.ts"
  isError:    false
}

toolCallId is the join key between the two rows — everything needed to reconstruct "the model asked for X, and got Y back" is these two rows plus their shared toolCallId, ordered by sequence.

04

Session → Interaction → Turn → Message

One interaction, two turns — this is the shape every tool-use exchange takes. The user's message opens the interaction directly (no turn yet); each provider call is its own turn box; every turn's messages nest inside it.

05

A request/response cycle, with real data

Tools execute on the user's machine, not the backend — the API server never has filesystem access. So each provider call is exactly one HTTP round trip: the stream closes the moment that call finishes, and if a tool needs running, the CLI makes a second, separate call once it has the result. Below is the full cycle for "list files in src and summarize the biggest one."

06

Compaction: made, stored, used, recovered

Compaction is checked right before every provider call, using the previous turn's inputTokens against that model's contextWindow (ModelCatalog). Crossing ~70% triggers it — asynchronously, so it never blocks the response the user is waiting on.

Step What happens Row written / read
Trigger Turn's inputTokens ≥ ~70% of contextWindow read AgentTurn.inputTokens, ModelCatalog.contextWindow
Summarize provider call over messages seq 1–28 read AgentMessage where sequence ≤ 28
Store insert one new row, nothing else touched AgentSessionCompaction{summary, coversFromSequence:1, coversToSequence:28}
Next context build newest compaction + everything after it summary text + AgentMessage where sequence > 28
Recover raw detail bypass compaction entirely sessions show --full reads AgentMessage with no lower bound
